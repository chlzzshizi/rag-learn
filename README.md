# rag-learn

手写 RAG，不用框架。目的是把「检索增强生成」的每一步都弄明白，而不是调通一个库。

## 语料

`Desktop/项目/2026-07-04-yunxi-redesign.md`（**73,785 字符** / 49 个标题，2026-09-19 量）

> 注意别把字节数和字符数搞混：这个文件是 132,542 **字节** / 72,819 **字符**。
> 中文一个字占 2-3 字节，用 `os.path.getsize()` 拿到的是字节数。

> ⚠️ **这个数字会一直变。** 09-14 量的时候是 48,738 字符（500 字符切块约 98 块），
> 09-19 已经涨到 72,819（约 146 块）—— 五天长了 2.4 万字。
> **所以块数不要背，每次跑脚本自己数。** 下面第 1 步给的那个区间，是用来对账的，
> 不是用来凑的；对不上就说明循环写错了，不是说明文档变了。

**注意：不复制到项目里**。脚本直接读原路径，这样你在开发 yunxi 时改了设计文档，
重跑脚本就能顺便练到增量更新。

## 技术选型

| 环节 | 用什么 | 关键参数 |
|---|---|---|
| 生成 | DeepSeek（`openai` SDK） | key 在 `.env`；**模型名也读 `.env`** |
| 检索 | Qwen3-Embedding-0.6B（本地 `models/`） | **1024 维 / 32K 上下文 / float32** |
| 向量检索 | 先 numpy 手算余弦，后换 faiss | 归一化后余弦 = 点积 |

选 0.6B 而不是 bge-small 的原因：**bge 整个 zh 系列上限都只有 512 token**，
而 Qwen3 是 32K —— 意味着**切块大小永远不会被模型卡住脖子**，你想切多大切多大。

> **2026-09-19 更正**：这里原先写着"500 个中文字符差不多是 400-550 token，
> 正好压线"，据此说 bge 会**静默截断**。**实测把这个理由推翻了**：
> 用这个模型的 tokenizer 数，500 个中文字符 = **358 token**。
> 358 < 512，bge 在 500 字符这一档**根本不会截断**。
>
> 所以"选 Qwen3 是因为 bge 会截断"这个说法在本项目里**不成立**。
> 真正成立的是：headroom 只有 1.4 倍（358 → 512），块长加到 700 字左右就压线了，
> 而第 1 步那个烂基线摆在那儿，**改块长是迟早的事**；再加上 Qwen3 本身是更新的模型。
> 选择仍然对，但理由要换。
>
> 留着的教训是那个机制本身：**超长会被静默截断，不报错、不警告**，
> 向量里少一段信息而你毫不知情。你后面检索不中会以为是切块策略的问题，
> 反复调参数，其实是被模型悄悄砍了。学 RAG 最怕这种错得没声音的 ——
> 换个模型、换个块长，这事随时会回来。

### ⚠️ 一定要用 float32 加载，别用默认的 bfloat16

`SentenceTransformer` 默认把模型读成 bfloat16。bfloat16 尾数只有 8 位，
归一化落不到精确的 1。实测：

| 精度 | 归一化后范数极差 | 148 块编码耗时 |
|---|---|---|
| bfloat16（默认） | 4.66e-03 | 73s |
| **float32** | **2.38e-07** | **138s** |

精度差 **19553 倍**，代价是**慢 1.88 倍**。148 个块就是 73 秒 vs 138 秒
（2026-09-19 用真实的 500 字块重测；batch_size=1，CPU）。

> 早先这里写的是"7 秒 vs 14 秒"，那是拿**短文本**测出来的，外推到真块上差了
> 10 倍。比率是对的，绝对值不能信 —— **基准测的不是你的数据，就等于没测。**

为什么这事重要：**"归一化后余弦 = 点积" 靠的就是范数精确等于 1**。
bfloat16 下它只是近似成立（点积与真余弦最大差 2.1e-3，实测 6 个样本里有 2 个
排序会变）。float32 下它是真的成立。差别只在两个候选几乎打平时才显现，
但你在学原理，不该让这个噪音混进来。

```python
import torch
model = SentenceTransformer(path, model_kwargs={"dtype": torch.float32})
```

## 网络：模型从 ModelScope 下，不走 HuggingFace

模型已经下好了，在 `models/Qwen3-Embedding-0.6B/`（1.15GB，`.gitignore` 忽略）。
`HF_HUB_OFFLINE=1` 都能跑通，**日常使用完全不需要网络**。

### 为什么不从 HuggingFace 下

实测：HF 上那个 1.19GB 的 `model.safetensors` **下不完**。

```
小文件（tokenizer.json, 11MB）      直连 7.5s  → 正常
大文件（model.safetensors, 1.19GB） 直连        → 每传 5-10MB 断一次
                                                 peer closed connection
                                                 重试到上限后放弃，删掉半截文件
```

断开的位置不固定（5MB / 7MB / 10MB 都出现过），但**同一个 CDN、同一台主机上的
小文件完全正常**——所以不是域名被墙，是大流量传输被中途重置。换成代理、换 hf-mirror
镜像都一样断。

**带 `Range` 头切段请求就不受影响**——这正是 `hf_hub_download` 续传时做的事，
所以它能一段段爬到 471MB，只是重试次数一到就整体放弃。

### 解决：换源到 ModelScope

Qwen 是阿里的模型，ModelScope 是它自己的官方源。同一个仓库，字节数完全一致
（`model.safetensors` 两边都是 1191586416）。

```bash
# 已经跑过了，除非换模型或者清空了 models/，否则不用再跑
.venv/Scripts/python.exe scripts/fetch_model.py
```

实测 **166 秒下完 1.15GB，零重试**（约 8MB/s）。

脚本用带 `Range` 的分段下载 + 断点续传，中途断了直接重跑就接着下。

> **踩过的坑**：ModelScope 的文件列表 API 默认只返回顶层，嵌套目录（如
> `1_Pooling/`）是以 `type=tree` 的条目出现的。不带 `Recursive=True` 的话，
> `1_Pooling/config.json` 会静默漏掉，然后加载时报
> `Pooling.__init__() missing 1 required positional argument: 'embedding_dimension'`。
> 脚本里已经修掉了。

### 代理的注意事项

如果你还是要手动下东西而挂代理：**不要把 `HTTPS_PROXY` 写进 `.env`**。
那样你的 DeepSeek 调用也会绕道代理——api.deepseek.com 是国内的，绕出去轻则变慢重则失败。
代理只给「当次下载命令」用，日常跑不加。

## 五步计划

### [ ] 1. 切块
读 md → 按固定长度切（先定 500 字符，不重叠）→ 打印块数和前几块

- [ ] 块数 == `ceil(字符数 ÷ 500)` —— 脚本自己算并打印，**不用记数字**
      （2026-09-19 是 73,785 字符 → 148 块）
- [ ] 肉眼翻一遍切口，**然后跑 `scripts/inspect_cuts.py` 对答案**
- [ ] 记下这个数字：**148 个切口里，落在换行处的有几个**

> 验收标准不是"找出 3 处切坏的"—— 那个说法是错的（2026-09-19 实测纠正）。
> 它暗示"坏的少、干净的多"，而实际情况是反过来：**0 个切口落在换行处**，
> 21 个切在代码块肚子里，23 个切在表格行中间，103 个切在句子中间。
> 没有一个是干净的。要看见的是这个"系统性"，不是"挑三个出来"。
>
> 所以第一步的结论应该长这样：**固定长度切块不是偶尔出错，是必然全错** ——
> 它只对齐长度，对内容边界零感知。这才是第 3 步要拿来做对照的烂基线。

> **块数是拿来对账的，不是拿来凑的。** 它的作用是：如果你切出 220 块，
> 说明循环写错了（比如每次只前进了一半）。如果你切出 146，说明循环是对的。
> 别为了让数字落进区间去调参数——那就本末倒置了。
>
> 而且这个区间**每次都要重算**（见上面「语料」一节的警告）：文档在长，
> 你下次来的时候 146 可能已经不对了。对不上先重算，再怀疑代码。

> 这一步别跳过。检索的问题 90% 出在这里。

### [x] 2. 编码落盘
编码所有块 → `data/chunks.jsonl` + `data/vectors.npy` + `data/manifest.json`

- [x] 向量形状 `(148, 1024)`，N == 块数
- [x] 重跑不会重新下载模型（模型已在 `models/`）
- [x] 每个 chunk 带 `chunk_hash` 和 `source_file`（为增量更新留位置）
- [x] 加载模型时传 `model_kwargs={"dtype": torch.float32}`（见上面「技术选型」）

**实测（2026-09-19）：**

| | |
|---|---|
| 产物 | `chunks.jsonl` 163,392 B / `vectors.npy` 606,336 B / `manifest.json` 427 B |
| 形状 | `(148, 1024)` float32 —— 148 × 1024 × 4 B = 606,208 B，和文件大小对得上 |
| 范数极差 | **2.38e-07**（bfloat16 会是 4.66e-03） |
| 端到端 | **164s**（其中模型加载约 15s） |
| 确定性 | 三次重跑范数极差**逐位相同**；`batch_size` 改了也不影响输出 |

**两个反直觉的点，都写进代码注释了：**

1. **`batch_size=1` 比 16 快 30%**（纯编码 14.65s vs 20.06s / 16 块）。
   CPU 上没有并行收益，批处理反而要按批内最长序列补齐。
   **但端到端只快 15%** —— 模型加载的 15s 是固定开销，稀释了比例。
   微基准的比例不能直接当端到端收益。
2. **500 个中文字符 = 358 token**（实测 tokenizer）。这个数推翻了上面
   「技术选型」里选 Qwen3 的原始理由，见那节的更正。

> 查询端要加指令前缀，文档端不加：
> `Instruct: 给定用户问题，检索能回答该问题的文档\nQuery: {问题}`
> v1 可以先不加，v2 加上做对比。
> （模型自带的 `config_sentence_transformers.json` 里已经有 query 的英文 prompt，
> 用 `model.encode(question, prompt_name="query")` 能直接调用。）

> **关于 `normalize_embeddings=True`**：这个模型的管线末尾自带 `Normalize` 模块，
> 所以 `encode()` 出来的**本来就已经归一化了**——实测开不开这个参数输出逐位相同，
> 它被当成冗余跳过了。写上无害（换别的模型可能就是必需的），但别以为
> "我归一化过了" 是靠这个参数起的作用。

### [ ] 3. 检索
问题编码 → 余弦相似度 → top-5

- [ ] 问「订单状态有哪些状态」→ **top-3 里出现状态机那一节**
- [ ] 检索不中时，**先回去看第 1 步的切块结果**，别改检索代码

### [ ] 4. 生成
top-k 拼进 prompt → 调 DeepSeek

- [ ] 回答含真实内容（"1. 待付款…"），不是编的
- [ ] 输出里能指出**答案来自哪一块**（便于排查）
- [ ] prompt 里明确要求「只根据给定资料回答，资料里没有就说不知道」

### [ ] 5. 评测
出 10 题，5 题答案集中在一段，5 题答案散在多处

- [ ] 前 5 题命中率接近 100%
- [ ] 后 5 题明显掉 —— **这个落差就是要看见的东西**

## 观察记录

### 第 1 步：固定长度切块的切口体检（2026-09-19）

语料 73,785 字符，按 500 字符不重叠切 → **148 块**。连续覆盖 0 → 73,785，
无缝隙、无重叠、无遗漏（`inspect_cuts.py` 的四项断言全过）。

**148 个切口落在哪：**

| 落在 | 个数 | 占比 |
|---|---|---|
| 行首（切在换行处） | **0** | 0.0% |
| 句中（切在行中间） | 103 | 70.1% |
| 代码块内部 | 21 | 14.3% |
| 表格行内部 | 23 | 15.6% |

语料含 16 个围栏代码块（11,562 字符）+ 29 张表格（11,615 字符），
合计占全文 **31.4%** —— 三分之一的内容是"不能被劈开"的结构。

**结论：不是"偶尔切坏"，是"系统性地全坏"。**

148 个切口没有一个落在换行处。这不是运气差：500 是整数，文档行长不是，
切口落在哪儿完全由前面所有行的累计长度决定。**固定长度切块只对齐长度，
对内容边界零感知。**

最典型的三处：

| 切口 | 偏移 | 被劈开的东西 |
|---|---|---|
| #124 | 62,000 | `CREATE TABLE coupons (` → `...coupo` \| `ns (...` |
| #12 | 6,000 | 类名 `PricePolicy` → `...PriceP` \| `olicy...` |
| #9 | 4,500 | YAML key `volumes:` → `...volume` \| `s:...` |

**`coupons` 这个词在索引里已经不存在了** —— 两个块各只有半个。向量模型
也许还能蒙对，关键词检索直接 miss。

表格被劈开更隐蔽（23 处）：数据行孤零零待在下一块，**列名留在上一块**。
切口 #32 的第二块开头是 `| 60.00（单独定价…） | 0.00 |` —— 单看这行，
你根本不知道这两列是"普洗/精洗"还是什么。检索命中它也没用。

**这份体检是第 3 步的对照基线。** 没有它，后面改语义切块时你无法说明
"改善了多少" —— 只能凭感觉说"好像好了点"。

复查工具：`scripts/inspect_cuts.py`（文档变了直接重跑，会重新算全部数字）。
