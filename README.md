用 LangChain 搭的 RAG，语料是自己的项目设计文档（云洗助手重构文档）。
**目标：先跑通一个能用的。**

> **2026-09-19 转向。** 这个项目一开始是**手写**的（不用框架），手写版做完
> 第 1 步切块、第 2 步编码，第 3 步检索写完没验证，然后决定换成 LangChain。
> 手写版的全部代码在 git `1963514`：
> ```bash
> git show 1963514:src/step1_chunk.py
> git checkout 1963514 -- src/     # 整个恢复
> ```
> 手写期间量到的数据**没有浪费**，全在下面的「观察记录」里，它们是 LangChain 版
> 的对照基线 —— 没有那组数字，你没法说 LangChain 到底改善了什么。

| 文件 | 字符 | 块数（`md` 切法，现用） | 块数（`flat` 切法，旧） |
|---|---|---|---|
| `Desktop/项目/2026-07-04-yunxi-redesign.md` | 73,820 | 204 | 215 |
| `D:\study\yunxi-server\docs\bug-record.md` | 124,886 | 334 | 332 |
| **合计** | **198,708** | **538** | **547** |

> **两种切法都在**（见「第 8 步」）。`flat` 是换切法之前的那套，**块数 547 可复现**
> （`--chunker flat`，或用 `.venv/Scripts/python.exe scripts/inspect_cuts.py --chunker flat`
> 单独数，不用编码）。换切法前记下的块号仍然对得上旧切法。

> ⚠️ **顺序不能改。** 索引里的块号 `i` 依赖它，顺序一变块号全变，
> 对着旧块号记的笔记就废了。

> 别把字节数和字符数搞混：设计文档是 **134,447 字节** / 73,785 **字符**
> （上面表里的 73,820 含 `# 文件：` 头，见下）。中文一个字占 2-3 字节，
> `os.path.getsize()` 拿到的是字节数。

> ⚠️ **这些数字会一直变。** 设计文档 09-14 量是 48,738 字符，09-19 上午 72,819，
> 09-19 晚上 73,785。**所以块数不要背，每次跑脚本自己数。**

`corpus_texts()` 给每份都加了 `# 文件：xxx` 头（两份共 57 字符），
**索引和长上下文两条路都走它** —— 两边拿到的字符串必须逐字节相同，
否则对照实验比的就不是检索策略了。

**不复制到项目里**。脚本直接读原路径，这样你在开发 yunxi 时改了文档，
重跑就能顺便练到增量更新。

> `data/` 里会有语料原文和 FAISS 索引，**都在 `.gitignore` 里**（白名单式：
> `data/*` + `!data/.gitkeep`）。

## 技术选型

| 环节 | 用什么 | 关键参数 |
|---|---|---|
| 切块 | `RecursiveCharacterTextSplitter` | `chunk_size=500` / `overlap=0` |
| 编码 | Qwen3-Embedding-0.6B（本地 `models/`，经 `HuggingFaceEmbeddings`） | **1024 维 / 32K 上下文 / float32** |
| 向量检索 | `FAISS`（`langchain-community`） | 归一化后余弦 = 点积 |
| 词面检索 | `rank_bm25` + `jieba`（分词，**必须先抠出标识符再交给 jieba**） | `k1=1.5` / `b=0.75`（库默认） |
| 融合 | RRF，自写（`src/hybrid.py`） | **`k=5`，不是教科书的 60** —— 见第 7 步 |
| 生成 | DeepSeek（经 `ChatOpenAI`，OpenAI 兼容） | key 和模型名都读 `.env` |
| 串联 | LCEL：`prompt \| llm \| StrOutputParser()` | — |

`langchain` 1.4.2。装上它**新增了 40 个包**（55 → 95）。

> ⚠️ **`langchain-community` 已被官方标记为 sunset**，FAISS 那个 import 属于它，
> 跑起来会打 `DeprecationWarning`。有个独立的 `langchain-faiss` 包，
> 但只有 **1.1 kB** —— 是个空壳，没装。

选 0.6B 而不是 bge-small 的原因：**bge 整个 zh 系列上限都只有 512 token**，
而 Qwen3 是 32K —— 意味着**切块大小永远不会被模型卡住脖子**。

> **2026-09-19 更正**：这里原先写着"500 个中文字符差不多是 400-550 token，
> 正好压线"，据此说 bge 会**静默截断**。**实测把这个理由推翻了**：
> 用这个模型的 tokenizer 数，500 个中文字符 = **358 token**。
> 358 < 512，bge 在 500 字符这一档**根本不会截断**。
>
> 所以"选 Qwen3 是因为 bge 会截断"这个说法在本项目里**不成立**。
> 真正成立的是：headroom 只有 1.4 倍（358 → 512），块长加到 700 字左右就压线了；
> 再加上 Qwen3 本身是更新的模型。选择仍然对，但理由要换。
>
> 留着的教训是那个机制本身：**超长会被静默截断，不报错、不警告**，
> 向量里少一段信息而你毫不知情。

### ⚠️ 一定要用 float32 加载，别用默认的 bfloat16

`SentenceTransformer` 默认把模型读成 bfloat16。bfloat16 尾数只有 8 位，
归一化落不到精确的 1。实测：

| 精度 | 归一化后范数极差 | 148 块编码耗时 |
|---|---|---|
| bfloat16（默认） | 4.66e-03 | 73s |
| **float32** | **2.38e-07** | **138s** |

精度差 **19553 倍**，代价是**慢 1.88 倍**（2026-09-19 用真实的 500 字块重测；
batch_size=1，CPU）。

> 早先这里写的是"7 秒 vs 14 秒"，那是拿**短文本**测出来的，外推到真块上差了
> 10 倍。比率是对的，绝对值不能信 —— **基准测的不是你的数据，就等于没测。**

为什么这事重要：**"归一化后余弦 = 点积" 靠的就是范数精确等于 1**。
bfloat16 下它只是近似成立（点积与真余弦最大差 2.1e-3，实测 6 个样本里有 2 个
排序会变）。float32 下它是真的成立。

**在 LangChain 里这么传**（注意 `model_kwargs` 嵌了两层，不是笔误）：

```python
HuggingFaceEmbeddings(
    model_name=str(MODEL_DIR),
    model_kwargs={"model_kwargs": {"dtype": torch.float32}, "device": "cpu"},
    encode_kwargs={"normalize_embeddings": True},
)
```

原因在 `langchain_huggingface/embeddings/huggingface.py:98`：
`model_cls(self.model_name, cache_folder=..., **self.model_kwargs)` ——
传进去的字典会被**展开成 `SentenceTransformer` 的直接参数**，而它不接受
直接的 `dtype`。写错的表现是 `TypeError: unexpected keyword argument 'dtype'`。

.venv/Scripts/python.exe scripts/eval_retrieval.py --retriever all     # 三路对照（默认）
.venv/Scripts/python.exe scripts/eval_answer.py              # 第 6 步：答案级，四臂对照

.venv/Scripts/python.exe scripts/eval_fuse_sweep.py
```

索引缓存在 `data/lc_index/`，第二次跑直接读，**不用重新编码**。

> ⚠️ **建索引很慢，而且慢得没有提示。** 538 块在 CPU 上实测 **13~17 分钟**
> （`torch` 用 float32 跑 0.6B 模型）。中途**没有任何进度输出**
> （stdout 被缓冲），只能靠 `tasklist` 看进程 CPU 在不在涨。
> 块数少了反而更慢 —— **这个数别背，它随机器负载变**。
> **别因为"没输出"就以为它死了**——但也要知道：索引没重建完时，旧索引还留在原地，
> `load_index()` **不会报错**，于是 RAG 臂看不到新语料而长上下文臂看得到，
> 对照实验静默作废。`eval_answer.py` 开头有个断言专门拦这个。

> ⚠️ **同时别跑两个**。两个进程各要 ~2.8GB，16GB 机器上互相抢 CPU，
> 实测把 10 分钟拖成 19 分钟。

## 网络：模型从 ModelScope 下，不走 HuggingFace

模型已经下好了，在 `models/Qwen3-Embedding-0.6B/`（1.15GB，`.gitignore` 忽略）。
**日常使用完全不需要网络**（DeepSeek 那次调用除外）。

### 为什么不从 HuggingFace 下

实测：HF 上那个 1.19GB 的 `model.safetensors` **下不完**。

```
小文件（tokenizer.json, 11MB）      直连 7.5s  → 正常
大文件（model.safetensors, 1.19GB） 直连        → 每传 5-10MB 断一次
                                                 peer closed connection
                                                 重试到上限后放弃，删掉半截文件
```

断开的位置不固定（5MB / 7MB / 10MB 都出现过），但**同一个 CDN、同一台主机上的
小文件完全正常**——不是域名被墙，是大流量传输被中途重置。换成代理、换 hf-mirror
镜像都一样断。

**带 `Range` 头切段请求就不受影响**——这正是 `hf_hub_download` 续传时做的事，
所以它能一段段爬到 471MB，只是重试次数一到就整体放弃。

### 解决：换源到 ModelScope

Qwen 是阿里的模型，ModelScope 是它自己的官方源。同一个仓库，字节数完全一致。

```bash
# 已经跑过了，除非换模型或者清空了 models/，否则不用再跑
.venv/Scripts/python.exe scripts/fetch_model.py
```

实测 **166 秒下完 1.15GB，零重试**（约 8MB/s）。

> **同一个病，PyPI 上也会犯**：`pip install langchain` 直连 PyPI 时，
> 响应 JSON 被截断成 `JSONDecodeError: Unterminated string`。换清华镜像
> （`-i https://pypi.tuna.tsinghua.edu.cn/simple`）就好了。
> 用一次性 `-i`，别写进 pip 配置。
>
> **09-20 又犯了一次，换了张脸**：装 `jieba`（19.2MB sdist）时 pythonhosted
> 只有 611 kB/s，拿到的文件**哈希不对**：
>
> ```
> ERROR: THESE PACKAGES DO NOT MATCH THE HASHES FROM THE REQUIREMENTS FILE.
>     Expected sha256 055ca12f62674fafed09427f176506079bc135638a14e23e25be909131928db2
>          Got        a5d1e353000eebb2cb350cf7b56177eead47fc3be532b84320c281ff896ec8f2
> ```
>
> 同样换清华源、加 `--no-cache-dir` 就过了（pip 会把坏包缓存下来，
> 不 `--no-cache-dir` 会一直拿同一个坏文件重试）。
> **两种表现同一个根因：大文件在直连 PyPI 上会被中途截断。**
> 小包（`rank_bm25` 才几十 KB）直连没事 —— **所以这个坑只在装大包时露头**。

> **踩过的坑**：ModelScope 的文件列表 API 默认只返回顶层，嵌套目录（如
> `1_Pooling/`）是以 `type=tree` 的条目出现的。不带 `Recursive=True` 的话，
> `1_Pooling/config.json` 会静默漏掉，然后加载时报
> `Pooling.__init__() missing 1 required positional argument: 'embedding_dimension'`。

**不要把 `HTTPS_PROXY` 写进 `.env`。** 那样你的 DeepSeek 调用也会绕道代理

   就不是切块的错**。原来那句「钉在了切块上（96.7% 切在词中间）」的 96.7%
   是个**测量假象**（详见第 8 步开头）。真按结构切完：结构缺陷（落单围栏
   22→0、无表头表格块 20→1）修掉了，**散落题 k=4 仍是 0%**。
3. **重跑第 6 步的对照实验** —— 它的 RAG 臂是旧检索，结论已被第 7 步动摇。
4. 再上 **LLM 拆题**（要调 DeepSeek，有 API 成本）
   —— 拿下文「实验一」的 oracle 拆分结果（0/5 → 2/5）当上界对照：
   **人工拆都只到 2/5，让 LLM 拆不会更好**

**真正该先补的是评测方法，不是检索方法**（第 6 步暴露的）：

- **锚点不能是"含表格/括号/markdown 的整句"** —— 单题摆幅实测 62 分。
  要么人工写"要点列表"式锚点，要么改用**按要点判分**而不是按字符串覆盖判分
- **16 题、单次运行不够下结论** —— 同一道题两次跑出过 190 字和 250 字两个答案，
  temperature=0 不保证确定。要下结论得每格跑 2~3 次，报逐题胜负而不是均值
- **补一个真正的随机对照**：把语料顺序反过来再跑一遍长上下文臂，
  看"答案在开头"这个位置红利到底值多少分

> **但也可以就到这儿。** 目标是"先跑通一个能用的 RAG"，它已经跑通了：
> **答案集中在一处的题，问得具体就能答对。** 而且现在**边界也量清楚了** ——
> 从"搭了一个 RAG"变成了"知道它什么时候不该用"。
> 这本身就是这一步的产出。

## 观察记录

### 第 5 步：检索评测 —— 集中题 100%，散落题 0%（2026-09-19）

10 题，5 题答案集中、5 题答案散落。**只测检索，不调 LLM** —— 切块坏了坏在
"召回的块里有没有那句话"，生成会把这个变量搅浑，还花钱。

| k | 集中题 | 散落题 |
|---|---|---|
| 1 | 80% | 0% |
| 2 | **100%** | 0% |
| 4 | 100% | 0% |
| 8 | 100% | 0% |
| **16** | **100%** | **0%** |

**计划预期的落差兑现了，而且比预期狠得多。** 集中题 k=2 就满分；
散落题从 k=1 到 k=16 一动不动，全是 0%。

> **k=16 是什么概念**：全语料 214 块，k=16 已经取回 7.5%。**加 k 完全没用。**

**为什么加 k 没用**：一个查询编码成**一个**向量，只能覆盖嵌入空间里的**一个邻域**。
这道文档把同一个知识点的不同侧面放在相隔上百块的地方（域层定义、数据库表、
接口清单、面试问答各一处），它们落在**不同的邻域**里。
**k 再大也只是把同一个邻域铺得更开，拉不来另一个邻域。**

已测的那两道题（订单状态、抢券超卖）能答对，是因为**它们恰好都是集中题**。
这不是巧合，是之前只测了容易的那一半。

#### 顺带排除了一个嫌疑：instruction 前缀

Qwen3-Embedding 的模型卡要求**查询端**加 instruction 前缀，文档端不加。
我们一直没加，是个很可疑的失分点。实测：

- 前缀**确实生效** —— 查询向量变了（与不加的余弦 0.903，不是 1.0）
- 结果**一个没变** —— 还是 100% / 0%

排除法做完，这个前缀不是这里的瓶颈。**但"加了没变"必须先证明"加了"**，
否则这是个假实验。

#### 切块损伤的量化：21 个答案块，9 块命中，6 块"差一块"

| 答案块 | 真命中 | **召回到的隔壁块（±1）** |
|---|---|---|
| 21 块 | 9 块 | **6 块** |

隔壁块的实例：召回 73（答案是 74）、召回 180（答案是 181）、
召回 28（答案是 27）、召回 82（答案是 81）。

**当时的推断是「切块边界在制造'差一块'」—— 这个推断后来被证伪了。**
第 8 步的 `audit()` 逐锚点查过：**0 条锚点被切块劈开**，一条都没有。
「召回到隔壁块」因此**不是**「答案被劈成两半」，而是**排序把答案块排到了第 5 位之后**
（第 5 步自己的 `min_cover` 也算过：k=4 对全部 16 道题都够装）。
不过原文那句「它不是散落题失败的原因」**是对的**，只是理由要说准：
散落题的答案分散在文档各处，**任何切法都凑不到一块去**。

#### 方法论上踩的两个坑（都差点把账算到检索头上）

1. **锚点用关键词 = 在量词频，不是量答案位置。** 第一版我用 `DECR` 当锚点，
   它落在 8 块里 —— 于是 5 道"集中题"全被算成散落。锚点必须收到
   **只在该答案处出现的整句**。
2. **这份文档会把同一件事说好几遍** —— 定义处一次、代码处一次、
   §11.8「面试四连问」再逐字答一次。只记一处锚点，检索召回了**另一处的
   等价答案**，就会被判成"噪音"。Q4 就是这样：第 196 块开头**就是那道题本身**，
   我判它噪音，**其实是检索答对了**。所以现在 `mode="any"`：
   集中题允许有多个等价答案，任一组凑齐就算答得出。

> **没做这两步之前，第一轮量出来的是"20% 全中"** —— 那个数字是错的，
> 错在标准答案，不在检索。**评测脚本的自检比评测结果本身更重要**：
> 它要能报出"锚点打错了""锚点跨块了"，否则你永远在量自己的笔误。

### 为什么散落题召不回 —— 三个实验（2026-09-20）

#### 实验一：拆题救得回多少？（oracle 拆分）

手工把每道散落题拆成 3 个子问题，各自检索，取并集。
**子问题是我知道答案之后写的 —— 这是天花板，不是系统能力。**

| | 凑齐 |
|---|---|
| 不拆题，单次 top-4（现状） | **0/5** |
| 拆题，每个子问题 top-1 | 0/5 |
| 拆题，每个子问题 top-2 | **2/5** |
| 拆题，每个子问题 top-3 | 2/5 |

**拆题有效，但救不全。** 所以"瓶颈是没拆题"这个判断**只对了一半**。

#### 实验二：那些句子到底能不能被搜到？

拿锚点**原文**当查询，看它所属的那一块排第几：

| 锚点原文 | 所属块 | 排名 |
|---|---|---|
| `门店单和网单都能用**（2026-09-12` | 74 | **第 1 名** |
| `管理员 403 只剩三处` | 29 | 第 3 名 |
| `auth:staff:invalidAfter:<staffId>` | 81 | 第 3 名 |
| `不参与订单操作，也不能改价` | 27 | **落榜** |
| `hasPassword()：门店单顾客从没设过密码` | 18 | **落榜** |
| `canLogin()：只有明确 status=1 才放行` | 18 | **落榜** |

**落榜的那几条，都埋在第 18 块 —— 那一块整个在 DDD 目录树里面**：

```
│       │   ├── WashType
│       │   ├── ClothesPrice
│       │   ├── PricePolicy    # "+20" 精洗派生规则的唯一住所
```

那两句话是**树里的注释**，向量被满屏 `│ ├──` 主导，任何自然语言提问都召不回。

> **方法论教训**：锚点按"唯一性"筛，会**系统性选中埋在代码块里的怪句子** ——
> 散文里的正常表述因为重复出现反而被筛掉。第一版的散落题就是这么被撑到
> 3~4 块跨度的。修掉这批过严锚点后，散落题最少只需 **2.2 块**，结论不变。

#### 实验三：同一个块，换个问法还能不能搜到？

目标固定为第 39 块（§4.3 那张"网单顾客 vs 门店单顾客"对照表）：

| 问法 | 排名 |
|---|---|
| 线上注册的顾客要不要填姓名 | **第 2 名** |
| 门店单顾客和网单顾客的建档方式有什么不同 | **第 4 名** |
| 门店单顾客的姓名和密码是什么状态 | 第 7 名 |
| 顾客有哪两种来源 | **落榜** |
| 网单顾客和门店单顾客有什么区别 | **落榜** |
| 会员和散客怎么区分 | **落榜** |

**规律：问法里带上块里的词（"建档方式"、"线上注册"、"姓名"）→ 排前几名；
问得更抽象（"有哪两种来源"）→ 落榜。**

> ## 结论：这个 0.6B 模型的稠密检索基本是「词面级」的，不是「语义级」的

这一条把所有观察串起来了：

| 现象 | 解释 |
|---|---|
| 集中题 100% | 它们和答案块**共享词汇** |
| 散落题 0% | 伞形提问和**任何一个块都不共享词汇**，而答案分散在词汇各异的块里 |
| 拆题 0/5 → 2/5 | 子问题更具体、更容易撞上词汇，但没救全 |
| k 加到 16 没用 | 加 k 只是把**同一个词汇邻域**铺开，拉不来别的邻域 |

#### 附带发现：markdown 语法会污染向量

洗掉 `|`、`│├└─`、` ``` `、`*` 等语法字符再编码，同一条查询的排名变化：

| 查询 | 目标块 | 原索引 | 去噪索引 |
|---|---|---|---|
| 管理员能不能操作订单和改价 | 27（表格） | 第 6 名 | **第 2 名** |
| 不参与订单操作，也不能改价 | 27（表格） | 落榜 | 第 17 名 |
| 顾客有哪两种来源 | 39（表格） | 落榜 | 落榜 |
| 员工账号什么状态才能登录 | 18（目录树） | 落榜 | 落榜 |

**去噪对第 27 块有效，对第 39、18 块无效。** 样本太小（各 1~2 条探针），
**不足以说"去噪对表格有用"** —— 记下来是因为它是个可复现的方向，不是结论。

### 第 7 步：混合检索 —— BM25 补上了稠密检索的短板（2026-09-20）

第 5 步诊断出「0.6B 稠密检索**基本是词面级匹配**」。那句话的后果是：
**这个检索器在用它不擅长的方式做它该做的事** —— 想匹配词面，但因为是向量
近似，匹配不准；又没有大模型的语义能力，跨不过「症状词 → 原因词」那一跳。

而词面匹配这件事本来就有专门做到极致的算法：**BM25**。纯 Python、零模型、
零成本。加进来跟稠密做 RRF 融合（`src/hybrid.py`）。

**为什么这一步可以放心测**：检索评测判的是「召回的块里有没有那句话」，
而块的正文是语料**逐字**切出来的 —— 不存在答案级评测那个「改写就不认账」的问题。
**第 5 步的数字可信、第 6 步的不敢信，差别就在这。**

> ⚠️ **第 8 步之后这句要加一个限定。** 块文本现在多了个 `[章节] …` 前缀
> （见第 8 步的「B」），它**不是正文的一部分**。前缀里的每个字仍然是从语料标题
> **逐字复制**的、不含任何改写，所以「块里有没有那句话」这条判据依然成立；
> 但「块 = 语料的逐字切片」这个说法**不再准确**，准确的说法是
> **「块的正文是语料的逐字切片」**。

#### 结果（k=4，16 题）

| | dense | bm25 | **hybrid** |
|---|---|---|---|
| 设计文档 × 集中 | 100% | 80% | **100%** |
| 设计文档 × 散落 | 0% | 0% | **0%** |
| bug文档 × 集中 | 20% | 60% | **60%** |
| bug文档 × 散落 | 0% | 100% | **100%** |
| **合计** | 6/16 | 8/16 | **9/16** |

> ⚠️ **这张表是旧索引（547 块，`flat` 切法）的数字，保留作第 7 步的原始记录。**
> 第 8 步换切法重建后（538 块，`md` 切法）同一张格子是
> **dense 8/16、bm25 7/16、hybrid 10/16**，对照见第 8 步。
> **差 1~2 题，在噪声内** —— 两版都别当结论用。

**融合在每个格子上都不低于最好的那条单臂**，逐题看也没漏掉任何一条单臂能找到的题。
而且它是**各取所长**：文档/集中拿 dense 的 100%、bug/集中拿 BM25 的 60% ——
两条单臂强在不同地方，这正是融合该起作用的场景。

BM25 单路本身已经是很大的实际收益：
**bug文档散落 0% → 100%，bug文档集中 20% → 60%。**

#### ⚠️ 差点报错的结论：教科书默认值害人

第一次跑出来是这样：

```
bug文档 集中   dense 20%   bm25 60%   hybrid 40%
bug文档 散落   dense  0%   bm25 100%  hybrid  0%    ← 融合把 BM25 赢的题弄丢了
```

**如果我停在这儿，结论就是「混合检索没用，老老实实用 BM25」。**
而且我会给它配一套听起来很合理的机制解释（"dense 是噪音，RRF 的共识被噪音
带偏"）—— 因为那个解释确实对得上，所以更难被怀疑。

于是我把整个参数格子扫了一遍（`scripts/eval_fuse_sweep.py`）。
**k 那一列是单调的：**

```
等权 k=1  →  56%        (0,1) 只用 BM25 → 50%   ← 单臂对照线
等权 k=5  →  56%        (1,0) 只用 dense → 38%
等权 k=20 →  44%
等权 k=60 →  38%        ← 和"只用 dense"一模一样
```

**是 RRF 的 k 用错了，不是融合本身不行。**

机制：k=60 时第 1~50 名只差 1.8 倍（`1/61=0.0164` → `1/110=0.0091`），
于是**任何块只要在两路里各出现一次、哪怕都在第 50 名，得 0.018，
就打赢只在单路排第 1 的 0.0164**。整个候选列表都落在被压平的区间里，
RRF 退化成「谁被两路都收进来谁赢」。

具体那题「明细 32 条」（bug 218）：

```
390   dense 第 1  + bm25 第 6   → 1/61 + 1/66 = 0.0315
218   bm25  第 1  + dense 第 17 → 1/61 + 1/77 = 0.0294   ← 输
```

**BM25 的第一名，输给了一个「两路都在中游」的块。**

**k=60 是从 TREC 那种上千深的候选列表里定出来的。** 这里列表只有 20~50 深，
差一个量级，k 得跟着缩。

旁证：把 BM25 权重加大到 3 倍、10 倍，结果都**退化回 50%（= BM25 单路）**
—— 融合的价值恰恰来自 dense 在那半边文档上的优势，压它就没价值了。
这跟「k=5 时最好」是同一件事的两面。

> ⚠️ **诚实交代**：k=5 是在**这 16 道题上**挑的，不是独立验证。可信度来自两处
> —— 趋势是单调的（不是撞上一个孤立的峰），机制也清楚。但别当它是定理。
> `src/hybrid.py` 里 `rrf_k` 默认是 5 而不是教科书的 60，**这是本仓库唯一一个
> 「默认值不是教科书值」的参数**，改它之前先看扫描表。

#### 怎么调都过不去的那个 0%

**设计文档 × 散落恒为 0%**，全格子无一例外 —— 权重、k、聚合方式全都动不了它。
当时写的归因是「**切块是头号嫌疑**（96.7% 切在词中间）」。

⚠️ **第 8 步把这个归因否掉了，两条独立证据：**

1. **96.7% 本身是测量假象** —— 真实值是 0.9%（见第 8 步开头）
2. **切法换掉了，散落题一分没动** —— k=4 仍是 0%，k=8 仍是 0%，直到 k=16 才到 20%
   （1/5 题，仍在噪声内）。而同一批改动确实修掉了 22 个落单围栏块和 20 个无表头表格块

所以散落题失败**是纯排序问题**，跟切块无关。要治得另开一步（改检索/改聚合）。

#### ⚠️ 这一步回头影响了第 6 步的结论

第 6 步的 RAG 臂用的是**旧的稠密检索**，而它量出的「检索是负收益」，
很大一部分**正是「检索没召回到答案」**：11 个长上下文胜里有 7 个是它把 RAG
漏掉的整段原文直接读到再转述。bug 文档那 6 道题就是明证 ——
**6 道里只有 1 道在 k=4 时召得回答案块。**

现在检索修好了（bug 文档 0% → 100%），**那个 11:1 的对照实验必须重跑**，
否则「检索是负收益」量的是「坏检索的代价」，不是「检索本身有没有用」。

重跑很便宜：32 次调用、语料缓存命中 99.8%、远低于 1 元。

### 第 8 步：切块 —— 从「500 字硬切」到「按结构切」（2026-09-20）

#### 先说一件不好听的：这一步的前提是错的

开工前写下的理由是「**547 块里 96.7% 的切口落在词中间**」。**这个数字是测量假象。**

它是 `scripts/inspect_cuts.py` 旧版测出来的，两个 bug 叠在一起：

1. 旧版分析的是**原始文件**，而块是从 `"# 文件：x.md\n\n" + 正文` 切的 —— **多 57 个字符**
2. 旧版用**块长累加**反推偏移（`offsets_of`），它假设块与块首尾相接。而 RCT 的
   `_join_docs` 会 `strip()` 每一片，误差**越滚越大**

平均行长约 55 字符 —— 于是那约 57 字符的偏移误差**恰好把每个偏移都打到行中间**。
指标在量自己的 bug，量出来的"坏切点"是它自己造的。

> **修好之后实测：`flat` 的 545 个切口里有 540 个（99.1%）落在行边界。**
> 不是 3.3%，是 99.1%。**旧切法的切口位置其实基本没问题。**

所以这一步的真实理由是**另一个缺陷**，那一条是量出来的、站得住的（见下表）：
**结构被撕碎**。这一条也解释了为什么这一步值得做 —— 但它跟"切口位置"无关。

#### 改了什么

三个改动，`src/chunking.py`（新文件，切块逻辑从 `rag.py` 搬出来独立成模块）：

| | 改动 | 做法 |
|---|---|---|
| **A** | 按标题切 | 自己写的**围栏感知**扫描（`md_sections`）。标题行**留在正文里** |
| **B** | 章节路径注入 | 每块正文前加一行 `[章节] 文档 > 七、优惠券 > 7.3 核销` |
| **C** | 围栏/表格安全 | 二次切分不撕开代码块和表格；切开时**补回 ``` 和语言标记、重复表头行** |

**没有用现成的 `MarkdownHeaderTextSplitter`**（虽然它是"标准答案"）：
`markdown.py:164` 对每一行做 `stripped_line = line.strip()` 再把**剥过的行**拼进
`page_content` —— `    Label: "1"` 出来变成 `Label: "1"`。这份语料满是缩进的
YAML/SQL/代码块，**缩进一丢就不是原文了**。只借了它两个正确的想法（围栏内不判标题、
标题进 metadata），扫描自己写。

#### 主判据：不依赖那 16 道题的硬指标

**这是这一步唯一该信的判据** —— 切口落哪、块里有没有落单围栏，跟题库无关。
（`scripts/inspect_cuts.py`，538 块 vs 547 块）

| 指标 | `md`（新） | `flat`（旧） | |
|---|---|---|---|
| 落单围栏块（` ``` ` 出现奇数次） | **0** | 22 | ✅ md |
| 无表头表格块（数据行丢了表头） | **1** | 20 | ✅ md |
| 干净块占比（不超长且无落单围栏） | **98.7%** | 96.0% | ✅ md |
| 超 500 字的块 | 7 | **0** | ❌ md |
| 切在行中间 | 6 (1.1%) | **5 (0.9%)** | ❌ md |
| 跨节块（前缀描述不到块尾） | 127 (23.6%) | **0** | ❌ md |

**是取舍，不是全面胜出，照实记。** 逐条：

- **22 → 0 和 20 → 1 是这一步的真收益**：22 个块里的代码是被劈开又没补围栏的、
  20 个块是**读不出每列是什么**的无表头数据行（原来那张 49 行 / 7594 字符的大表
  被切成 20 段，只有第 1 段带表头）
- **7 个超长块（最大 856 字）换来的是那 22 和 20**。查过：这 7 块的**最长行是
  354~530 字符**（表格行、长 JSON 行），不切开行就没法再切。切了就会掉回旧切法的样子
- **`跨节块 127` 是 B 的已知代价**：合块是跨节界的，所以一个块可能「开头在 §2.1、
  结尾已经进了 §3」，而 `[章节]` 前缀只描述得到块首。**这是这一步引入的新缺陷**，
  不是遗留的

#### 命中率：跟旧数字对比（`eval_retrieval.py --sweep`，k=4）

对照的是**第 7 步已经记在 README 里的旧数字**（旧索引 547 块）：

| k=4 | dense | bm25 | hybrid |
|---|---|---|---|
| 设计文档 × 集中 | 100% → 100% | 80% → 80% | 100% → 100% |
| 设计文档 × 散落 | 0% → 0% | 0% → 0% | 0% → 0% |
| bug文档 × 集中 | 20% → **40%** | 60% → **40%** | 60% → **80%** |
| bug文档 × 散落 | 0% → **100%** | 100% → 100% | 100% → 100% |
| **合计** | 6 → **8** | 8 → **7** | 9 → **10** |

**按开工前写死的判据报：**

- **hybrid 9 → 10、bm25 8 → 7，都是 ±1 题，一律报「无变化」。**
  16 道题，1 题 = 6.25%，这个量级分辨不了
- dense 6 → 8 是 **+2 题，刚好在噪声边缘**。**两条臂方向还不一致**（一条 +1、一条 −1）
  —— 这个形状更像噪声，不像信号。**不当结论用**
- 机制上唯一有理由的是：bug 文档的块注入了 `[章节] … > Bug 12 > 根因`，
  把"Bug 12"这个正文里不重复出现的标识提到了块首 —— 但**这只是个假说，
  16 道题验不了它**

#### 免费筛被验证了（这是方法论上唯一站得住的一处）

重建索引前用 **BM25 单路零编码成本**筛过一遍（`scripts/eval_chunker_screen.py`），
筛出的 `md + 注入 + 结构安全` 是 **7/16 @k4、9/16 @k8**。

**重建后实测 bm25 正是 7/16 @k4、9/16 @k8。** 两处都精确命中 ——
说明**免费筛对最终索引是忠实的**，以后换切法可以先零成本筛、再付那一次稠密编码。

筛还给出了另一个**扛得住噪声**的结论：**合块是必须的，不是可选优化** ——
不合块 4~5/16，合块 8~9/16，差 3~4 题，是量级差别。机制也清楚：
naive 按标题切会产出 16,588 字符的单块，在 BM25 的长度归一化下永远赢不了。

> 筛里还有一行 `n=3、均值 7.4 万字符、16/16` 看着像巨大胜利，**那是假的** ——
> 那是"把整个语料当三块喂进去"，是**长上下文那一臂的成绩**，不是检索的。
> 差点被它骗过去。

#### 散落题：这次能确定不是切块的错了

开工前不敢下这个判断。现在能了，**两条独立证据**：

1. `audit()` 逐锚点查过：**0 条锚点被切块劈开**，0 条打错字
2. 切法整个换掉了，**设计文档 × 散落 k=4 仍是 0%、k=8 仍是 0%**，
   到 k=16 才到 20%（1/5 题，仍在噪声内）

而同一批改动确实修掉了 22 个落单围栏块、20 个无表头表格块。
**切块修好了，散落题一分没动 → 散落题失败是纯排序问题。**

#### B 的收益有天花板（写在前头，免得以后误读）

`[章节]` 路径里每个字都是语料自己的标题，不含任何改写。但**路径的信息量 = 标题的信息量**：

- 设计文档的标题是 `七、优惠券 > 7.3 核销` —— **给得起信号**
- bug 文档的 254 个 H3 大量复用 `现象 / 根因 / 修复 / 教训` 这种无区分度的词，
  125 个不同标题值撑起 307 个标题 —— **给不起信号**

**所以 B 对设计文档那半边有用、对 bug 文档那半边接近于平。** 预期如此，不是 bug。

**⚠️ 它还有一个副作用必须记住**：块文本现在多了 `[章节] …` 前缀，**它不是正文的一部分**。
「块 = 语料的逐字切片」这个说法**不再准确**，准确的说法是
**「块的正文是语料的逐字切片」**。前缀逐字来自标题、不含改写，
所以检索评测的「块里有没有那句话」这条判据依然成立。

#### 顺手查出的两个 bug（都是这一步引入/发现的）

1. **围栏被切开时，第 0 片的定位锚退化成了裸 ` ``` `** —— 3 个字符，原文里到处都是，
   `_locate` 于是匹配到**别的那道围栏**，`p.offset` 落到别的节里（实测 538 块里 2 块）。
   **影响面**：`Piece.path`（进 `[章节]` 前缀、被编码的东西）**一直是对的**，
   错的只是 `offset`（只有 `inspect_cuts.py` 用）。
   **已修**：锚改成「围栏行 + 首行正文」。**改锚不改文本 → 不用重新编码**，
   块数 538/547 一字未变
2. **`inspect_cuts.py` 新增的「跨节块」指标第一版有假阳性** —— 它从零搭路径，
   块里若只有 `### 1.2` 而没有祖先 `## 一、`，搭出来就缺级、跟完整路径一比全成了跨节。
   改成**用 `piece.path` 起头**后，与独立方法（按偏移算）分别给出 127 和 134，
   **两个方法互相印证**（偏移法会把块外的尾巴也算进去，所以略高）

这两个 bug 都不是靠肉眼发现的，是**先写指标、再看指标报警**找到的 ——
这也是这一步最值钱的产出：`inspect_cuts.py` 现在有了「偏移自洽失败」一列，
**非 0 就说明锚定位有 bug，按偏移算的切口分类全部作废**。

#### 怎么用

```bash
.venv/Scripts/python.exe scripts/inspect_cuts.py                  # 硬指标体检（两种切法对比）
.venv/Scripts/python.exe scripts/eval_chunker_screen.py           # 换切法前先免费筛（零编码）
.venv/Scripts/python.exe src/rag.py "..." --rebuild --chunker md   # 按结构切（默认）
.venv/Scripts/python.exe src/rag.py "..." --rebuild --chunker flat # 旧切法，复现 547 块
```

**索引现在会自述**：`build_index` 把切法/块数/语料 sha256 写进 `data/lc_index/build.json`，
`load_index` 读它挂成 `store.chunker_meta`，**三个评测脚本都会把它打出来**。
缺这个文件就大声警告（老索引或手工拷来的）。

> 为什么非加不可：有了 `--chunker` 之后，**谁跑一次 `--chunker flat` 建索引，
> 之后所有评测都会读到 flat 建的东西却以为看的是新的**。数字会静默作废。

### 第 6 步：长上下文对照实验 —— 检索到底帮了忙没有（2026-09-20）

**结论：这个语料上，检索是负收益。**

同语料、同题、同模型（`deepseek-flash`，temperature=0）、**同 prompt**
（两臂共用 `longctx.build_messages()`，指令只有那一处定义），
只换「资料」那一段：RAG 臂给检索 top-4，长上下文臂给整份语料。
16 题（10 道设计文档 + 6 道 bug 记录）× 2 臂，32 次调用。

| | RAG 胜 | 长上下文胜 | 平 | 题数 |
|---|---|---|---|---|
| 设计文档 × 集中 | 1 | 2 | 2 | 5 |
| 设计文档 × 散落 | 0 | 4 | 1 | 5 |
| bug文档 × 集中 | 0 | 4 | 1 | 5 |
| bug文档 × 散落 | 0 | 1 | 0 | 1 |
| **合计** | **1** | **11** | **4** | **16** |

「胜」= 3-gram 覆盖减掉跨题蒙中地板后差 > 10 分。**不看均值** —— 单题摆幅实测
最大 62 分，n=5 时一题翻面就动均值 20 分，均值没有分辨力（理由见下）。
**而那唯一的「RAG 胜」是假的**，也是读原文才发现的。

⚠️ **这张表是第 7 步（加 BM25）和第 8 步（换切块）之前的**，
两步都改过 RAG 臂拿到的东西。**重跑结果见本节的「重跑」一小节** ——
结论方向没变，幅度变了（8:2 ~ 10:1）。
表里这个 `1 : 11 : 4` 现在**能用 `scripts/eval_verdict.py` 复现**
（在此之前它是人工数出来的，仓库里没有脚本能重算）。

#### 先修掉一个错前提：窗口不是 128K，是 1M

第 5 步我从"散落题 0%"推出"该上多路召回"。那个推论**建立在一个错的前提上**：
我以为上下文窗口是 128K。实际 `deepseek-flash` / `deepseek-v4-pro` 是 **1M**
（V4 起；128K 是上一代 V3.2 的数）。

| | 字符 | Qwen 分词器 | **DeepSeek 实收** |
|---|---|---|---|
| 设计文档 | 73,820 | 41,139 | |
| bug-record.md | 124,886 | 72,368 | |
| **合计** | **198,708** | **113,534** | **103,560** |

⚠️ **两个 token 数别混**：本地 Qwen 分词器数出 113,534，DeepSeek 实收 **103,560**
—— 分词器不同，**Qwen 系统性高估约 9%**。`longctx.py --stats` 用的是 Qwen，
那是个**代理值**，不是计费口径。

⚠️ **语料是 198,708 字符，不是 198,651** —— `corpus_texts()` 给每份都加了
`# 文件：xxx` 头（共 57 字符），早期的估算漏了它。

113K 占 1M 的 10.4%，**塞得下**。所以该先回答的不是"怎么修检索"，
而是"这个语料上检索带来了什么"。

#### 缓存：99.8% 命中，成本可忽略

语料放前、问题放后（DeepSeek 缓存要求**从第 0 个 token 起前缀逐字节相同**）。
长上下文臂 16 次调用：输入 1,657,117 tokens，**命中 1,653,504（99.8%）**；
输出 19,558。RAG 臂输入 15,176 / 输出 24,419。**整个实验远低于 1 元。**

三个坑，都踩过：

- **语料里有 147 处花括号**（`{couponId}`、`{staffId}`…）。任何对语料调 `.format()`
  都会 `KeyError`。走 messages 列表 + 纯字符串拼接，**不经过任何模板引擎**。
- **缓存不改变模型行为**（同样的 token 进去，同样的计算），只影响价格。
  别把它读成"缓存让答案变好了"。
- 命中率只在**长上下文臂内**有意义，两臂不可比 —— RAG 臂实测 9.3%
  （它那段固定指令头碰巧命中的），**那不是故障**，别按 0% 去报警。

#### ⚠️ 判分器差点骗了我 —— 四个指标全坏，靠**人读**才发现

这一段是这步最值钱的部分。四个指标在正式跑之前都"看着没问题"：

**① `strict`（锚点逐字出现）量的不是"答对没有"，是"有没有照着原文抄"。**

    锚点  「精洗价直接手动填写」（语料原文）
    答案  「精洗价**就**直接手动填写」        ← 只多一个「就」
    → 一个完全正确的答案，strict 判 0%

而长上下文臂拿 100%，因为它**逐字复述**了原文（还带引号和 §编号）。
**谁手里的原文多谁赢** —— 这是抄袭探测器，方向系统性偏向长上下文臂。
补了 `strict_fuzzy`（容许 1 个字的插入/删除/替换）才让"答对但改了字"不被判 0。

**② 跨题蒙中地板用"相邻的下一题"是错的 —— 它凭空造出一个假的「RAG 赢」。**

原设计拿本题答案去对下一题的锚点，量"纯蒙能得多少分"。
「支付报 500」（Bug 1）那题，长上下文臂的地板竟有 **92%** ——
因为它 1137 字的答案里**连 Bug 2 的原文都抄进去了**（相邻两条 bug 互相引用、
同属一个模块）。于是 `gram - null` 把 **100% 的正确答案压成 8%**，算出"RAG 赢"。

**相邻题不是随机对照，是高度相关的对照。** 改成取半程之外的题，
地板从 0~92% 收到 **0~21%**，那个假「RAG 赢」当场消失。

⚠️ **但"当场"是假的 —— 这次改动改完没有重跑。** 2026-09-20 逐行核过 dump：
16 题 4 臂存下来的 `gram_null` **全部是 `i+1` 规则**（无一例外），
所以"地板收到 0~21%、假胜消失"这件事**当时没有任何运行记录**。
现在能用 `eval_verdict.py` 验证（结果见下面「重跑」一节的表），结论对，
但这条记述得改成"机制上成立、当时未验证"。

**③ `ident`（抽标识符）在这份语料上大面积作废。**
一半锚点是纯中文（`| 4 | 待出厂 | 洗涤完成 |`、`不参与订单操作，也不能改价`），
一个标识符都抽不出 → 整个题该指标作废，汇总里标「—」。
留着它是为了**如实报出"这个指标不能用"**，不是因为它有用。

**④ 拒答检测器误判，产出了一条假结论。**
最初写成"出现「资料里没有提到」就算拒答"，而 RAG 臂答完精洗价的正常规则和例外后，
收尾说「资料里没有提到除此之外的其他例外」—— 那是**按 prompt 规则 2 如实划定边界**，
却被记成弃答，汇总里凭空多出"RAG 拒答 1 次"。**一个答对的答案被记成弃权。**
加了长度条件（真拒答很短）才修好。

#### 人读出来的三件事（计划里那条"最终防线"确实拦住了东西）

自动指标跑完看着挺清楚，抽读 3 道题 × 2 臂之后变了：

| 题 | 指标说 | 读原文发现 |
|---|---|---|
| 订单状态码 1-7 | 长上下文 0% / RAG 100%（**唯一的 RAG 胜**） | **长上下文答对了** —— 它自己重排了两列表，省掉「含义」列；而**问题只问"叫什么"，没问含义**。是**锚点多要了一列** |
| 快递单号上限 | RAG 0% / 长上下文 100% | **RAG 答对了** —— 锚点要 `不是 length()`，它写了更准确的 `不是 String.length()`。**锚点比答案更苛刻** |
| 明细 32 条 | RAG 0% / 长上下文 100% | **RAG 真失败** —— 召回到的是别的 bug 块，它老实说「资料里没有提到」，还列出了资料实际覆盖的内容 |

**3 道里 2 道是锚点的锅。** 锚点是从语料里抄的整句，而语料句子自带表格、括号、
markdown —— 这些是**任何正确的改写都不必复现**的格式。这是这套判分的**系统性缺陷**：

> **单题摆幅实测最大 62 分。** 所以「设计文档 × 集中 82% vs 86%」**落在噪声里，
> 不能下结论**；逐题胜负表（1 : 11 : 4）比均值稳，但也只到这个精度。

（这跟第 5 步踩的是**同一个坑**：`eval_retrieval.py` 的文档里早写着
"标准答案不认账，不是检索失败" —— 我在答案级又犯了一遍。）

#### 那到底能说什么

**能说的**（差距远大于噪声，且有机制支撑）：

1. **散落题上检索在丢答案。** 设计文档散落 5 题 RAG 是 0 胜 4 负 1 平；
   第 5 步的检索评测也早就是 0%（k=16 仍是 0%）。**两条独立证据指向同一件事。**
2. **bug 文档上更糟，6 道只答对 1 道。** 原因在检索评测里很清楚：
   **6 道题只有 1 道在 k=4 时召得回答案块**。查询用的是症状语言
   （"为什么调用支付接口报 500"），答案躺在原因语言里
   （"`save()` 写死了 `orderMapper.insert()`"）—— 0.6B 的稠密检索跨不过这一跳。
3. **长上下文赢的不是"检索得更好"，是"它根本不需要检索"** ——
   11 胜里有 7 胜是把 RAG 漏掉的整段原文直接读到再转述。

**不能说的**（写清楚，免得被上面的数字带跑）：

1. **不能推广成"长上下文比 RAG 强"。** 16 道题、一个语料、单次运行；
   temperature=0 **也不保证确定** —— 同一道题两次跑出过 190 字和 250 字两个答案。
2. **布局对长上下文最有利。** 语料在前、问题在后是**缓存逼出来的**，
   而它恰好把答案放在最有优势的位置（21 个设计文档锚点全在前 41K tokens 内）、
   问题放在最后（近因效应）。**测的是"长上下文最有利时的表现"，不是它的能力上界。**
3. **两臂的资料「形式」也不同**，不只是内容：RAG 臂拿到的是切碎的片段
   （标题被切掉、句子被劈开），长上下文臂拿到完整 markdown。
   这是**呈现方式的劣势**，混在"检索的锅"里了。
4. **长上下文臂话更多、抄更多**（整臂平均 **857 字 vs 351 字**，复述率 **81% vs 64%**）。
   减掉跨题蒙中地板后差距仍在，但这**三个偏差同向**，别当它是干净的 11:1。

   ⚠️ 这里原本写的是「1083 字 vs 276 字」—— **那两个数是 `bug文档/集中` 单格的均值
   被当成了整臂均值**（2026-09-20 复核 dump 时发现）。整臂是 857 vs 351，
   复述率 81%/64% 倒是跟 dump 对得上。

#### 重跑：换了切块和检索之后，11:1 变成 8:2（2026-09-20 晚）

上面那 1 : 11 : 4 是在**第 7 步（加 BM25 混合检索）和第 8 步（换切块）之前**跑的。
两步都改过 RAG 臂实际拿到的东西，所以那个数字跟仓库里的代码已经对不上 —— 重跑一次。
同时把三臂都跑齐（dense / bm25 / hybrid），这样"换更好的检索能不能翻盘"有个直接答案。

跑法：`eval_answer.py --arms dense,bm25,hybrid,long`，16 题 × 4 臂 = 64 次调用，
`data/answers_20260920_223019.jsonl`。长上下文臂缓存命中 **99.9%**（1,654,784 / 1,657,117），
成本可忽略。

| 对照臂 | 设计/集中 | 设计/散落 | bug/集中 | bug/散落 | **合计** | 均值 delta（**参考，不判胜负**） |
|---|---|---|---|---|---|---|
| dense（= 旧的 `rag` 臂） | 1-2-2 | 0-2-3 | 0-4-1 | 1-0-0 | **2 : 8 : 6** | 43.4 vs 75.1 |
| bm25 | 0-3-2 | 0-3-2 | 0-4-1 | 1-0-0 | **1 : 10 : 5** | 43.4 vs 75.1 |
| hybrid | 0-3-2 | 0-3-2 | 1-2-2 | 1-0-0 | **2 : 8 : 6** | 53.8 vs 75.1 |

**结论方向没变：三条 RAG 臂全部大幅输给长上下文。** 但幅度从 11:1 缩到 8:2~10:1，
而且**换了最好的检索器并没有翻盘** —— hybrid 的合计跟 dense 一样是 2:8:6
（均值 delta 高 10 分，但那不算判据）。

**⚠️ 幅度变小这件事本身不能归因。** 这次重跑同时动了三样东西：切块（547→538）、
检索（dense→三臂）、以及判分脚本 —— 而且 `temperature=0 也不保证确定`
（旧跑 long 臂整臂均值 857 字，这次 824 字，同一套 prompt；**分格看抖得不小** ——
`设计文档/集中` 625 → 537、`bug文档/集中` 1083 → 1005，`设计文档/散落` 867 → 914）。
**要断言"切块+混合检索让差距缩小了"，得每格跑 2~3 次。**
单次运行的 ±1~2 题变化按本项目的规矩一律报「无变化」。

##### 人读抽了 4 道（照规矩来，不只看分），其中 2 道推翻了指数的读法

**① 换了检索器，逐题会动，但合计判决不动。**

三对臂的 top-4 **平均只有 55% 重合、16 题里只有 1 题完全相同**
（dense 和 bm25 在「Redis 存了什么」那题上 0/4 重合）—— 检索器确实是不同的检索器。
逐题 delta 也确实跟着动：

| 对比 | 中位差 | ≤ 1 分的题 | ≤ 5 分的题 |
|---|---|---|---|
| dense vs bm25 | 3.8 分 | 6/16 | 9/16 |
| dense vs hybrid | 8.3 分 | 4/16 | 7/16 |
| bm25 vs hybrid | 1.3 分 | 8/16 | 9/16 |

**但合计判决三臂几乎一样（1~2 : 8~10），而且没有任何一臂翻盘。**
（个别题差得很大 —— dense 那次拒答就是 100 分，但那正是上面 ④ 里查清的检索给错。）

> **"选哪路检索"在答案层面几乎不改变结论。** 这解释了为什么第 7 步检索评测里
> 混合检索明明赢了（k=4 上 10/16 vs 稠密 8/16），到答案层面却兑不出来 ——
> **检索指标（答案块进没进 top-k）和答案质量（最终答对没有）之间有一步巨大的损耗**，
> 中间隔着"模型怎么用这几块"。第 5→6 步之间其实早就撞见过同一件事
> （"差一块"的 6 块里很多并不影响答对）。

**② 两场「RAG 胜」读原文之后都是措辞artifact，不是质量胜。**

| 题 | 指标 | 读原文 |
|---|---|---|
| 快递单号上限（dense +15） | dense `gram=1.00` / long `0.85` | **同一件事**。锚点要 `不是 length()`，dense 照抄了 `length()`，long 写成更准确的 `String.length()` → 3-gram 断了。**跟原版实验里人读发现的完全同一个坑** |
| 同一顾客快速点两次抢券（三臂都胜，+39~+49） | RAG `0.86~0.96` / long `0.49` | **long 答得最全**：它是四份里唯一给出修复代码和原文「教训」那节的。锚点要「写操作顺序**错误**：先写缓存（SADD）后写数据库（insert）」，long 写的是「写操作顺序**错了**」+「先 `SADD` 后 `insert`」—— 意思全在，措辞被拆开 |

> **这个判据奖励逐字复述。** 长上下文臂是**在被惩罚的前提下**赢的 8~10 题；
> 而 RAG 那两场「胜」是复述胜。**别把 2:8 读成"RAG 有两成时候更好"。**

**③ 但 long 最大的那场胜是真内容胜 —— 而且机理清楚。**

「项目里 Redis 存了哪些东西」dense 输 85 分。读原文：dense 给出 2 个键
（`coupon:stock:` / `coupon:grabbed:`）并老实说「资料里没有提到其他 Redis 键名」；
long 给出**全部 4 个**（另两个是 `blacklist:token:` / `auth:staff:invalidAfter:`）。
**这道题的两组锚点正好一半在设计文档、一半在 bug 文档** —— top-k 天然给不齐，
而长上下文两半都看得到。**这才是长上下文在散落题上的真实优势来源。**

**④ dense 那次唯一的拒答，是检索给错了，不是模型摆烂。**

「一个订单明明只有一条明细，却查出 32 条」dense 答「资料里没有提到。」——
核了它的 4 个召回块（387/391/393/396）：**全部是 Bug 43（空明细白洗）的连续块，
没有一块含 `insertBatch`**。查询说的是"明细条数"，它匹配到了另一个也讲"明细"的 bug。
bm25/hybrid 都召回了块 208（Bug 2 正文），gram=1.00。
**拿错上下文时模型拒答而不硬编 —— 这是模型诚实，不是模型无能。**

##### 该记下来的两件事

1. **旧那个 1:11:4 现在可复现了**，而且**重算才发现它当时是怎么来的复现不出来**：
   dump 里存的地板全是废弃的 `i+1` 规则（逐行核过），正确规则和裸 `gram` 都给 1:11:4，
   只有 `i+1` 给 2:10:4（假胜在 bug/集中 那格）。**两个错法的合计恰好一样。**
   判据写进 `scripts/eval_verdict.py` 了，以后不靠手数。
2. **判据的系统性缺陷已经量到位了**：它测的是"有没有照着原文抄"。
   要修得改判据本身（比如锚点用短标识符而不是整句），**不在本次范围** ——
   但**读这张表的时候必须带着这个偏差**，两个方向都要带。

#### bug 文档那 6 道题是怎么来的

选题规则是机械的（**用户拍板 + 无判断的抽取**），值得记一笔：

- 原本想用"每 10 条取 1 条"，**实测被否决** —— 抽出的 5 条里只有 2 条像样的题，
  Bug 21/31/41 是**测试脚本元 bug**（"`bench-coupon.sh` 量的是 JVM 冷启动"），
  没人会这么问；**文档后半段从领域 bug 漂移成了测试工具 bug**
- 改成规则抽 49 条候选、**由用户挑**。用户选"订单/状态机、并发/数据一致、权限/安全
  三组各两条"，**具体编号用机械规则定：每组取列出的前两条** → 1、2 / 10、11 / 16、20
- **Bug 16 和 Bug 20 的`修复`/`验收`节都被后续口径修订作废了**
  （Bug 20 的修复代码甚至成了死代码，原文自己标注"这就是本条最讽刺的地方"）。
  所以这两题的锚点**只取`根因`和`教训`** —— 锚在作废段落上，
  等于拿语料自己说已过时的话去判分

### 手写固定切块 vs LangChain 递归切块（2026-09-19）

**同样 `chunk_size=500`、`overlap=0`：**

| 切法 | 块数 |
|---|---|
| 手写固定切块 | **148** |
| LangChain `RecursiveCharacterTextSplitter` | **214** |

**多出 66 块**，块长也确实参差不齐了（14 ~ 498，平均 343），不再是清一色 500。

**但体检结果显示：它没有更好，甚至略差。**

| | 手写固定切块 | LangChain 递归切块 |
|---|---|---|
| 块数 | 148 | 214 |
| 切口数 | 147 | 213 |
| 落在换行处 | 0 (0.0%) | 3 (1.4%) |
| 句/词中间 | 103 (70.1%) | **144 (67.6%)** |
| 代码块内部 | 21 (14.3%) | 34 (16.0%) |
| 表格行内 | 23 (15.6%) | 32 (15.0%) |
| **硬伤占比** | **29.9%** | **31.0%** |

把切点前后各看 30 个字符，重新数一遍（防止"换行符留在下一块开头"导致漏判）：
**213 个切口里，206 个（96.7%）两边都不是换行 —— 切在词中间。**

> # ⚠️ 上面这一段是错的 —— 2026-09-20 查实，保留原文作记录
>
> **96.7% 这个数是 `inspect_cuts.py` 旧版的测量假象，不是切块器的行为。**
> 两个 bug 叠出来的：① 旧版分析**原始文件**，而块是从 `"# 文件：x.md\n\n" + 正文`
> 切的，**差 57 个字符**；② 旧版用**块长累加**反推偏移，而 RCT 的 `_join_docs`
> 会 `strip()` 每一片，误差越滚越大。平均行长约 55 字符，
> 于是那约 57 字符的误差**恰好把每个偏移都打到行中间**。
>
> **修好后实测（`flat` 547 块）：545 个切口里 540 个（99.1%）落在行边界。**
>
> 下面那两个"被劈开"的例子（偏移 1,188 / 1,648）**也是这么造出来的，不是真的。**
>
> **所以这一节的结论「换了 LangChain 切块问题一点没解决」只在"结构被撕碎"这条上成立
> （那条是真的，见第 8 步），在"切口位置"这条上恰好说反了：**
> RCT 确实把切口从行中间的硬切换成了在 `\n\n` / `\n` / 中文标点处断句，
> 只是旧指标看不见这件事。**左边那列手写固定切块的数字（148 块那列）不受影响** ——
> 固定长度切块的偏移是 `i*500` 算出来的，不需要反推。

**原因：分隔符列表掉到了最后一档。** 配置是
`["\n\n", "\n", "。", "；", "，", " ", ""]` —— **中文没有空格**，
`" "` 这一档几乎切不动任何东西，于是直接落到 `""`，
**退化成逐字符硬切**，切点又变回由 500 这个整数决定。

> **结论：换了 LangChain，切块问题一点没解决。**
> 它给的是**管道**（Document / Retriever / Chain 那套抽象），不是**更好的切法**。
> 想让它真按中文句子切，得把分隔符改对（去掉 `" "` 和 `""`，
> 或者换 `MarkdownHeaderTextSplitter` 按 49 个标题切）—— 这跟用不用框架无关。
>
> **这正是第 1 步那个体检的价值**：没有它，你会以为"换了框架就好了"。

### 手写第 1 步：固定长度切块的切口体检（2026-09-19）

语料 73,785 字符，按 500 字符不重叠切 → **148 块**。连续覆盖 0 → 73,785，
无缝隙、无重叠、无遗漏（`inspect_cuts.py` 的四项断言全过）。

**148 个切口落在哪：**

| 落在 | 个数 | 占比 |
|---|---|---|
| 行首（切在换行处） | **0** | 0.0% |
| 句中（切在行中间） | 103 | 70.1% |
| 代码块内部 | 21 | 14.3% |
| 表格行内部 | 23 | 15.6% |

语料含 16 个围栏代码块（11,562 字符）+ 29 张表格（11,615 字符），
合计占全文 **31.4%** —— 三分之一的内容是"不能被劈开"的结构。

**结论：不是"偶尔切坏"，是"系统性地全坏"。**

148 个切口没有一个落在换行处。这不是运气差：500 是整数，文档行长不是，
切口落在哪儿完全由前面所有行的累计长度决定。**固定长度切块只对齐长度，
对内容边界零感知。**

最典型的三处：

| 切口 | 偏移 | 被劈开的东西 |
|---|---|---|
| #124 | 62,000 | `CREATE TABLE coupons (` → `...coupo` \| `ns (...` |
| #12 | 6,000 | 类名 `PricePolicy` → `...PriceP` \| `olicy...` |
| #9 | 4,500 | YAML key `volumes:` → `...volume` \| `s:...` |

**`coupons` 这个词在索引里已经不存在了** —— 两个块各只有半个。

表格被劈开更隐蔽（23 处）：数据行孤零零待在下一块，**列名留在上一块**。
单看 `| 60.00 | 0.00 |` 你根本不知道这两列是什么。检索命中它也没用。

**这份体检是上面的对照基线。** 没有它，你无法说明 LangChain 改善了多少
—— 只能凭感觉说"好像好了点"。
