## 技术选型

| 环节 | 用什么 | 关键参数 |
|---|---|---|
| 切块 | `RecursiveCharacterTextSplitter` | `chunk_size=500` / `overlap=0` |
| 编码 | Qwen3-Embedding-0.6B（本地 `models/`，经 `HuggingFaceEmbeddings`） | **1024 维 / 32K 上下文 / float32** |
| 向量检索 | `FAISS`（`langchain-community`） | 归一化后余弦 = 点积 |
| 生成 | DeepSeek（经 `ChatOpenAI`，OpenAI 兼容） | key 和模型名都读 `.env` |
| 串联 | LCEL：`prompt \| llm \| StrOutputParser()` | — |

`langchain` 1.4.2。装上它**新增了 40 个包**（55 → 95）。

> ⚠️ **`langchain-community` 已被官方标记为 sunset**，FAISS 那个 import 属于它，
> 跑起来会打 `DeprecationWarning`。有个独立的 `langchain-faiss` 包，
> 但只有 **1.1 kB** —— 是个空壳，没装。

选 0.6B 而不是 bge-small 的原因：**bge 整个 zh 系列上限都只有 512 token**，
而 Qwen3 是 32K —— 意味着**切块大小永远不会被模型卡住脖子**。

> **2026-09-19 更正**：这里原先写着"500 个中文字符差不多是 400-550 token，
> 正好压线"，据此说 bge 会**静默截断**。**实测把这个理由推翻了**：
> 用这个模型的 tokenizer 数，500 个中文字符 = **358 token**。
> 358 < 512，bge 在 500 字符这一档**根本不会截断**。
>
> 所以"选 Qwen3 是因为 bge 会截断"这个说法在本项目里**不成立**。
> 真正成立的是：headroom 只有 1.4 倍（358 → 512），块长加到 700 字左右就压线了；
> 再加上 Qwen3 本身是更新的模型。选择仍然对，但理由要换。
>
> 留着的教训是那个机制本身：**超长会被静默截断，不报错、不警告**，
> 向量里少一段信息而你毫不知情。

### ⚠️ 一定要用 float32 加载，别用默认的 bfloat16

`SentenceTransformer` 默认把模型读成 bfloat16。bfloat16 尾数只有 8 位，
归一化落不到精确的 1。实测：

| 精度 | 归一化后范数极差 | 148 块编码耗时 |
|---|---|---|
| bfloat16（默认） | 4.66e-03 | 73s |
| **float32** | **2.38e-07** | **138s** |

精度差 **19553 倍**，代价是**慢 1.88 倍**（2026-09-19 用真实的 500 字块重测；
batch_size=1，CPU）。

> 早先这里写的是"7 秒 vs 14 秒"，那是拿**短文本**测出来的，外推到真块上差了
> 10 倍。比率是对的，绝对值不能信 —— **基准测的不是你的数据，就等于没测。**

为什么这事重要：**"归一化后余弦 = 点积" 靠的就是范数精确等于 1**。
bfloat16 下它只是近似成立（点积与真余弦最大差 2.1e-3，实测 6 个样本里有 2 个
排序会变）。float32 下它是真的成立。

**在 LangChain 里这么传**（注意 `model_kwargs` 嵌了两层，不是笔误）：

```python
HuggingFaceEmbeddings(
    model_name=str(MODEL_DIR),
    model_kwargs={"model_kwargs": {"dtype": torch.float32}, "device": "cpu"},
    encode_kwargs={"normalize_embeddings": True},
)
```

原因在 `langchain_huggingface/embeddings/huggingface.py:98`：
`model_cls(self.model_name, cache_folder=..., **self.model_kwargs)` ——
传进去的字典会被**展开成 `SentenceTransformer` 的直接参数**，而它不接受
直接的 `dtype`。写错的表现是 `TypeError: unexpected keyword argument 'dtype'`。

## 网络：模型从 ModelScope 下，不走 HuggingFace

模型已经下好了，在 `models/Qwen3-Embedding-0.6B/`（1.15GB，`.gitignore` 忽略）。
**日常使用完全不需要网络**（DeepSeek 那次调用除外）。

### 为什么不从 HuggingFace 下

实测：HF 上那个 1.19GB 的 `model.safetensors` **下不完**。

```
小文件（tokenizer.json, 11MB）      直连 7.5s  → 正常
大文件（model.safetensors, 1.19GB） 直连        → 每传 5-10MB 断一次
                                                 peer closed connection
                                                 重试到上限后放弃，删掉半截文件
```

断开的位置不固定（5MB / 7MB / 10MB 都出现过），但**同一个 CDN、同一台主机上的
小文件完全正常**——不是域名被墙，是大流量传输被中途重置。换成代理、换 hf-mirror
镜像都一样断。

**带 `Range` 头切段请求就不受影响**——这正是 `hf_hub_download` 续传时做的事，
所以它能一段段爬到 471MB，只是重试次数一到就整体放弃。

### 解决：换源到 ModelScope

Qwen 是阿里的模型，ModelScope 是它自己的官方源。同一个仓库，字节数完全一致。

```bash
# 已经跑过了，除非换模型或者清空了 models/，否则不用再跑
.venv/Scripts/python.exe scripts/fetch_model.py
```

实测 **166 秒下完 1.15GB，零重试**（约 8MB/s）。

> **同一个病，PyPI 上也会犯**：`pip install langchain` 直连 PyPI 时，
> 响应 JSON 被截断成 `JSONDecodeError: Unterminated string`。换清华镜像
> （`-i https://pypi.tuna.tsinghua.edu.cn/simple`）就好了。
> 用一次性 `-i`，别写进 pip 配置。

> **踩过的坑**：ModelScope 的文件列表 API 默认只返回顶层，嵌套目录（如
> `1_Pooling/`）是以 `type=tree` 的条目出现的。不带 `Recursive=True` 的话，
> `1_Pooling/config.json` 会静默漏掉，然后加载时报
> `Pooling.__init__() missing 1 required positional argument: 'embedding_dimension'`。

### 代理的注意事项

**不要把 `HTTPS_PROXY` 写进 `.env`。** 那样你的 DeepSeek 调用也会绕道代理
—— api.deepseek.com 是国内的，绕出去轻则变慢重则失败。代理只给「当次命令」用。

（`git push` 到 github 是另一回事，那台机器连 github 时通时不通，见
`yunxi-git-push-two-remotes` 那条记忆。）

## 观察记录

### 第 5 步：检索评测 —— 集中题 100%，散落题 0%（2026-09-19）

10 题，5 题答案集中、5 题答案散落。**只测检索，不调 LLM** —— 切块坏了坏在
"召回的块里有没有那句话"，生成会把这个变量搅浑，还花钱。

| k | 集中题 | 散落题 |
|---|---|---|
| 1 | 80% | 0% |
| 2 | **100%** | 0% |
| 4 | 100% | 0% |
| 8 | 100% | 0% |
| **16** | **100%** | **0%** |

**计划预期的落差兑现了，而且比预期狠得多。** 集中题 k=2 就满分；
散落题从 k=1 到 k=16 一动不动，全是 0%。

> **k=16 是什么概念**：全语料 214 块，k=16 已经取回 7.5%。**加 k 完全没用。**

**为什么加 k 没用**：一个查询编码成**一个**向量，只能覆盖嵌入空间里的**一个邻域**。
这道文档把同一个知识点的不同侧面放在相隔上百块的地方（域层定义、数据库表、
接口清单、面试问答各一处），它们落在**不同的邻域**里。
**k 再大也只是把同一个邻域铺得更开，拉不来另一个邻域。**

已测的那两道题（订单状态、抢券超卖）能答对，是因为**它们恰好都是集中题**。
这不是巧合，是之前只测了容易的那一半。

#### 顺带排除了一个嫌疑：instruction 前缀

Qwen3-Embedding 的模型卡要求**查询端**加 instruction 前缀，文档端不加。
我们一直没加，是个很可疑的失分点。实测：

- 前缀**确实生效** —— 查询向量变了（与不加的余弦 0.903，不是 1.0）
- 结果**一个没变** —— 还是 100% / 0%

排除法做完，这个前缀不是这里的瓶颈。**但"加了没变"必须先证明"加了"**，
否则这是个假实验。

#### 切块损伤的量化：21 个答案块，9 块命中，6 块"差一块"

| 答案块 | 真命中 | **召回到的隔壁块（±1）** |
|---|---|---|
| 21 块 | 9 块 | **6 块** |

隔壁块的实例：召回 73（答案是 74）、召回 180（答案是 181）、
召回 28（答案是 27）、召回 82（答案是 81）。

**所以切块边界确实在制造"差一块"** —— 因为切口落在句子中间，
答案被劈成两半，另一半的上下文块反而更像查询。但它**不是散落题失败的原因**：
散落题的答案本来就分散在文档各处，任何切法都凑不到一块去。

#### 方法论上踩的两个坑（都差点把账算到检索头上）

1. **锚点用关键词 = 在量词频，不是量答案位置。** 第一版我用 `DECR` 当锚点，
   它落在 8 块里 —— 于是 5 道"集中题"全被算成散落。锚点必须收到
   **只在该答案处出现的整句**。
2. **这份文档会把同一件事说好几遍** —— 定义处一次、代码处一次、
   §11.8「面试四连问」再逐字答一次。只记一处锚点，检索召回了**另一处的
   等价答案**，就会被判成"噪音"。Q4 就是这样：第 196 块开头**就是那道题本身**，
   我判它噪音，**其实是检索答对了**。所以现在 `mode="any"`：
   集中题允许有多个等价答案，任一组凑齐就算答得出。

> **没做这两步之前，第一轮量出来的是"20% 全中"** —— 那个数字是错的，
> 错在标准答案，不在检索。**评测脚本的自检比评测结果本身更重要**：
> 它要能报出"锚点打错了""锚点跨块了"，否则你永远在量自己的笔误。

### 手写固定切块 vs LangChain 递归切块（2026-09-19）

**同样 `chunk_size=500`、`overlap=0`：**

| 切法 | 块数 |
|---|---|
| 手写固定切块 | **148** |
| LangChain `RecursiveCharacterTextSplitter` | **214** |

**多出 66 块**，块长也确实参差不齐了（14 ~ 498，平均 343），不再是清一色 500。

**但体检结果显示：它没有更好，甚至略差。**

| | 手写固定切块 | LangChain 递归切块 |
|---|---|---|
| 块数 | 148 | 214 |
| 切口数 | 147 | 213 |
| 落在换行处 | 0 (0.0%) | 3 (1.4%) |
| 句/词中间 | 103 (70.1%) | **144 (67.6%)** |
| 代码块内部 | 21 (14.3%) | 34 (16.0%) |
| 表格行内 | 23 (15.6%) | 32 (15.0%) |
| **硬伤占比** | **29.9%** | **31.0%** |

把切点前后各看 30 个字符，重新数一遍（防止"换行符留在下一块开头"导致漏判）：
**213 个切口里，206 个（96.7%）两边都不是换行 —— 切在词中间。**

```
偏移 1,188   …见第二  |  段补记）：        ← "第二段" 被劈开
偏移 1,648   …作为账  |  目轨迹保留）      ← "账目" 被劈开
```

**原因：分隔符列表掉到了最后一档。** 配置是
`["\n\n", "\n", "。", "；", "，", " ", ""]` —— **中文没有空格**，
`" "` 这一档几乎切不动任何东西，于是直接落到 `""`，
**退化成逐字符硬切**，切点又变回由 500 这个整数决定。

> **结论：换了 LangChain，切块问题一点没解决。**
> 它给的是**管道**（Document / Retriever / Chain 那套抽象），不是**更好的切法**。
> 想让它真按中文句子切，得把分隔符改对（去掉 `" "` 和 `""`，
> 或者换 `MarkdownHeaderTextSplitter` 按 49 个标题切）—— 这跟用不用框架无关。
>
> **这正是第 1 步那个体检的价值**：没有它，你会以为"换了框架就好了"。

### 手写第 1 步：固定长度切块的切口体检（2026-09-19）

语料 73,785 字符，按 500 字符不重叠切 → **148 块**。连续覆盖 0 → 73,785，
无缝隙、无重叠、无遗漏（`inspect_cuts.py` 的四项断言全过）。

**148 个切口落在哪：**

| 落在 | 个数 | 占比 |
|---|---|---|
| 行首（切在换行处） | **0** | 0.0% |
| 句中（切在行中间） | 103 | 70.1% |
| 代码块内部 | 21 | 14.3% |
| 表格行内部 | 23 | 15.6% |

语料含 16 个围栏代码块（11,562 字符）+ 29 张表格（11,615 字符），
合计占全文 **31.4%** —— 三分之一的内容是"不能被劈开"的结构。

**结论：不是"偶尔切坏"，是"系统性地全坏"。**

148 个切口没有一个落在换行处。这不是运气差：500 是整数，文档行长不是，
切口落在哪儿完全由前面所有行的累计长度决定。**固定长度切块只对齐长度，
对内容边界零感知。**

最典型的三处：

| 切口 | 偏移 | 被劈开的东西 |
|---|---|---|
| #124 | 62,000 | `CREATE TABLE coupons (` → `...coupo` \| `ns (...` |
| #12 | 6,000 | 类名 `PricePolicy` → `...PriceP` \| `olicy...` |
| #9 | 4,500 | YAML key `volumes:` → `...volume` \| `s:...` |

**`coupons` 这个词在索引里已经不存在了** —— 两个块各只有半个。

表格被劈开更隐蔽（23 处）：数据行孤零零待在下一块，**列名留在上一块**。
